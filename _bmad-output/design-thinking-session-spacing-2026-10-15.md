# Design Thinking Session: Gloam 플레이 패널의 여백

**Date:** 2026-10-15
**Facilitator:** Codex
**Workflow:** BMAD CIS `bmad-cis-design-thinking`
**Execution:** 사용자의 자율 분석·설계·구현·검증·푸시 지시에 따라 체크포인트 승인을 반복하지 않고 진행했다.

## Design Challenge

사용자가 제공한 15:10 화면에서 시간 배지, 세션 시작 버튼, 세션 종료 질문이 붙어 서로 다른 절차를 구분하기 어렵다. 플레이 중 다음 행동을 빠르게 찾으면서 고딕 제목·종이색·44px 입력창·3440px 대응을 유지해야 한다.

## EMPATHIZE: Understanding Users

### User Insights

사용자의 직접 피드백은 ‘여백 부족. 디자인 점검 바람’이다. 캡처는 세션 시작과 정산 사이의 간격이 사실상 없음을 보여 준다. 추가 사용자 인터뷰나 5–7명 사용성 조사는 수행하지 않았다.

### Key Observations

Empathy Mapping, Journey Mapping, Shadowing 관점으로 실제 화면을 검토했다. 관찰 근거는 사용자 캡처와 앱의 현재 렌더링이다. 사용자가 세션 상태 확인 → 시작 → 종료 조건 확인 → 경험치 정산을 순서대로 읽어야 하지만, 각 단계가 같은 밀도로 붙어 있다. `session-xp`에 구조적 간격이 없고 개별 버튼에만 임의의 5px 마진이 있었다. 공통 폼도 12px 간격이며, 1280px에서는 상태 표시줄의 좌우 여백이 사라졌다.

### Empathy Map Summary

말: 여백이 부족하다. 행동: 문제 위치를 캡처해 전달했다. 필요: 다른 절차와 연결된 컨트롤을 시각적으로 구별할 수 있어야 한다. 생각과 감정은 직접 확인하지 않았으므로 추정 사실로 쓰지 않는다.

## DEFINE: Frame the Problem

플레이어는 세션을 시작하거나 마칠 때 현재 상태와 다음 절차를 빠르게 구분해야 한다. 같은 묶음 안의 간격과 절차 사이의 간격이 같거나 없는 것이 원인이다. 어떻게 조작 수를 늘리지 않으면서 관계 있는 요소는 가깝게, 다른 절차는 충분히 떨어뜨릴 수 있을까?

## IDEATE: Generate Solutions

Brainstorming, SCAMPER Design, Analogous Inspiration으로 대안을 만들었다.

1. 상태와 시작 버튼 사이에 일정한 간격을 둔다.
2. 시작과 정산 사이를 구분선으로 나눈다.
3. 정산을 의미 있는 section으로 묶는다.
4. 정산 제목과 설명을 정렬한다.
5. 경험치 체크박스를 하나의 묶음으로 정리한다.
6. 막간 계획 입력 앞에 추가 간격을 둔다.
7. 정산 버튼과 완료 안내를 같은 흐름으로 둔다.
8. 버튼의 임의 5px 마진을 없앤다.
9. 공통 폼의 행·열 간격을 나눈다.
10. 버튼 행의 줄바꿈 간격을 늘린다.
11. 패널 제목과 본문의 간격을 통일한다.
12. 단독 버튼 뒤 설명이 붙는 경우를 공통으로 고친다.
13. 상태 표시줄의 좌우 여백을 본문에 맞춘다.
14. 시작과 종료를 별도 화면으로 분리한다.
15. 종료 조건을 접어서 기본 화면을 줄인다.
16. 모든 패널을 더 큰 카드로 만든다.

선택한 세 개념은 ‘절차별 묶음과 간격’, ‘공통 폼의 리듬’, ‘본문과 상태 표시의 좌우 정렬’이다. 별도 화면·접기는 추가 조작과 숨겨진 정보를 만들고, 패널 전체 확대는 서로 붙은 내부 요소를 해결하지 못하므로 채택하지 않았다.

## PROTOTYPE: Make Ideas Tangible

별도 이미지 모형 없이 실제 JSX와 CSS로 프로토타입을 만들었다. 상태→시작 버튼 16px, 정산 앞 28px와 구분선 뒤 24px, 정산 내부 16px, 체크박스 묶음 내부 8px로 정리했다. 공통 폼은 행 18px·열 16px, 버튼 행은 행 10px·열 12px, 패널 제목 뒤는 20px로 통일했다. 입력/선택 높이 44px는 유지했다. 1280px 상태 표시줄도 본문과 같은 24px 여백을 갖는다.

## TEST: Validate with Users

### Testing Plan and Feedback

사용자의 캡처를 실패 사례로 삼아 390×844와 3440×1440의 실제 브라우저에서 간격과 가로 넘침을 검사했다. 1280px에서는 비술·전투·인물·플레이 화면의 레이아웃도 확인했다. 사용자에게 수정 후 별도 평가를 받았다고 주장하지 않는다.

### Key Learnings

브라우저 실측에서 상태→버튼 16px, 정산 영역 전 간격 28px, 시작 버튼→정산 제목 53px를 확인했다. 두 크기에서 선택창은 44px이고 가로 넘침이 없다. 1280px의 비술·전투 입력창도 모두 44px이며 공통 폼 간격이 18px·16px로 적용됐다. 상태 표시줄 시작점은 모바일 15px, 1280px에서 25px이다(앱 테두리 포함).

화면 폭과 제목의 고딕 인상만으로 내부 여백이 검증되지는 않는다. 앞으로는 ‘상태→행동→다음 절차’의 실제 거리도 확인한다. 수치는 `validation/rulebook-audit-2026-10-15/spacing-layout-measurements.json`, 이미지는 같은 폴더의 `spacing-session-desktop.png`와 `spacing-session-mobile.png`에 보관한다.

## Next Steps

58개 규칙/화면 이벤트 검사·운영 빌드·ESLint를 다시 실행하고 규칙 수정과 함께 푸시한다. 새 사용자 피드백에서는 조작을 추가하지 않고 절차의 구분이 충분한지 우선 확인한다. 실제 모바일 기기의 터치 평가와 다수 사용자 조사는 이번 범위에 포함하지 않았다.
