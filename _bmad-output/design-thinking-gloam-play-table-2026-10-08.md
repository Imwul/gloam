## 🎯 Design Challenge

이 작업은 기존 화면을 기준으로 룰북을 재분류하는 작업이 아니다. 먼저 제공된 Gloam1.02 본문 60쪽, 공식 Combat Example 3쪽, Character Sheet 1쪽, 총 64쪽을 처음부터 끝까지 읽었다. Goals와 Instincts가 이야기를 이끌고, 허구 속 행동 선언 → 필요할 때만 판정 → 결과·자원·관계 갱신 → 다음 행동으로 돌아오는 루프를 독립적으로 추출했다. 그 이후 현재 앱을 실제 브라우저에서 감사했다.

설계 성공은 사용자가 이야기의 다음 행동을 실행하고, 규칙과 현재 인물 상태를 확인하고, 결과를 정확히 반영하는 데 필요한 이동과 선택이 줄어드는 것이다. 이전 레이아웃과 기능의 배치는 제약으로 두지 않았다. 보존 가치가 있는 상태·저장·원문 자료는 유지하되, 그 관리 기능이 플레이보다 먼저 보일 이유는 없다.

근거는 [독립 룰북 검토](independent-rulebook-review-2026-10-08.md), [기존 앱 UX 감사](baseline-ux-audit-2026-10-08.md), 동결된 기준선 `/tmp/gloam-baseline`, 그리고 수정된 `src/App.tsx`, `src/play/PlayTable.tsx`, `src/play/QuickRules.tsx`, `src/rules.ts`, `src/index.css`다. 기준선은 Chrome/Playwright로 데스크톱 1440×900과 모바일 390×844에서 관찰했다. 신규 앱은 1440·768·390·340px의 6개 주요 화면을 검증했다. 아래 사용자 사고·감정에 관한 진술은 이 자료를 바탕으로 한 설계 가설이며 인터뷰 인용이 아니다. 최종 인증 결과는 [플레이 경험 검증 보고서](validation/play-experience-report.json)에 기록한다.

BMAD의 Empathize → Define → Ideate → Prototype → Test 구조와 템플릿을 적용했다. `design-methods.csv` 전체를 읽고, 프로젝트 resolver에서 사용자 지정 선행·후행 단계와 persistent facts가 비어 있음을 확인했다. 사용자가 분석부터 구현·검증까지 자율 진행하도록 명시했으므로 중간 승인 체크포인트는 운영하지 않았다.

## 👥 EMPATHIZE: Understanding Users

### User Insights

주 사용 맥락은 한 인물을 관리하면서 플레이하는 플레이어이며, 같은 도구에서 적과 사건을 운용하는 심판 역할도 고려했다. 솔로 플레이에서는 사건·징조가 대화 상대를 대신하므로 주변 기능이 아니라 반복 도구가 된다. 모바일은 테이블 위에서 한 손으로 확인하는 상황, 데스크톱은 인물과 행동 도구를 동시에 보는 상황을 설계 가설로 삼았다. 실제 참가자 인터뷰나 현장 플레이 관찰은 하지 않았다.

선택한 방법은 Journey Mapping, Empathy Mapping, Shadowing이다. 앞의 두 방법은 독립 룰북 분석과 브라우저 과업 관찰로 작성했다. Shadowing에 해당하는 실제 사람 관찰은 실시하지 못했으며, 대신 자동화된 과업 walkthrough로 조작·스크롤·상태 전환을 기록했다. 이 대리 활동으로 실제 사람의 학습 속도나 만족도를 주장하지 않는다.

| 플레이 여정 | 사용자가 이루려는 일 | 필요한 정보·도구 | 기존 마찰 | 설계 대응 |
|---|---|---|---|---|
| 세션 시작 | 인물을 떠올리고 오늘의 목적을 잡는다 | 목표 3개, 본능, 상태, 양측 결의 | 기본 화면은 긴 생성 기록지; 목표는 모바일 Y2269 | 기본 플레이 탁자, 공통 상태 줄, 현재 목표·본능 요약 |
| 행동 선언 | 장비·시간·계획으로 가능한지 확인한다 | 실제 능력치, 장비, 판정 필요 조건 | 판정 폼은 이유·문양·중복 능력치 등 여러 입력부터 제시 | 불확실할 때만 판정 안내, 실제 능력치 버튼, 이유는 선택 |

| 탐사·장면 전환 | 사건을 받고 세계에 질문한다 | 환경, 사건·징조 표, 시간 | 사건 앞에 지도 16칸; 징조 앞에 비술·연금술 | 사건·징조·환경·시간을 한 구역에 배치 |

| 전투 | 손패 → 선제권 → 행동 → 피해를 이어간다 | 숨긴 선제권, 대항 여부, 부위·AP·결의 | 손패와 행동 카드 재선택; 피해 대상·값 재입력 | 전투 전용 작업 공간, 손패의 행동 선택, 결과의 피해 준비 |
| 목표·본능의 변화 | 성취·좌절을 다음 장면의 연료로 바꾼다 | 결의 획득 조건, 새 목표 | 이야기 엔진이 생성 폼 깊숙이 있고 상태를 별도로 편집 | 목표 완수·불가능 버튼, 본능의 문제·이야기 변화 조건 명시 |
| 휴식·세션 끝 | 부상을 회복하고 성장·막간을 기록한다 | 식사와 밤, 선택 부상, 1–3 XP, 계획 | 반복 XP 버튼으로 같은 이유를 여러 번 더할 수 있음 | 조건 확인 휴식, 세션 시작·정산 상태, 체크리스트·막간 계획 |

### Key Observations

측정치는 콘텐츠 영역의 문서 상단 Y 좌표이며, 앱 응답 시간이나 사람의 수행 시간은 아니다. 첫 기준선 촬영에는 폰트 로딩 차이가 있었고, 폰트가 해결된 재실행에서도 같은 패널 좌표를 확인했다.

기준선의 가로 문서 overflow는 390px에서 없었다. 그러나 가로 overflow가 없다는 사실만으로 사용성이 입증되지는 않는다. 반복 도구가 여러 화면 아래에 묻혀 있었다.

기준선 조작 수는 개별 버튼·선택 컨트롤 기준이며 스크롤과 텍스트 포커스를 제외했다. 일반 판정·사건·징조는 초기 인물 화면에서 각각 탭 이동과 뽑기로 2회였지만, 사건과 징조는 위 표만큼 아래에 있었다. 고용인 판정 준비는 막간 → preset → Tests → 뽑기로 4회였다. 신규 적을 준비하고 조준 공격·피해까지 진행하는 시나리오는 19개 컨트롤, 이미 진행 중인 라운드의 행동·피해는 최대 10개 컨트롤을 사용했다. 전투 결과에 플레이어 결의를 더하는 기능은 없었다.

UI 뒤의 판정 규칙도 감사했다. 결의 획득과 심판 자원 증가가 연결되지 않고 소비 시 심판에게 증가하던 문제, 로마 숫자 Major 카드가 0으로 계산되어 사기 판정이 항상 실패하던 문제, 갑옷이 없는 타격도 흠집으로 판정하던 경계, 오래된 궁정 카드 별칭의 계산 오류를 확인했다. 이를 화면 장식으로 해결할 수는 없다.

## 🎨 DEFINE: Frame the Problem

### Point of View Statement

플레이어는 이야기의 행동을 선언하는 순간에 자신의 목적·능력·상태와 필요한 판정 절차를 한곳에서 확인해야 한다. Gloam의 중심은 목표를 좇는 허구 속 행동이며, 책의 장별 분류를 탐색하느라 대화를 멈추면 이 루프가 끊기기 때문이다.

심판은 만남의 반응, 사건, 적의 상태, 전투 순서와 피해 적용을 현재 장면에 맞게 이어서 운용해야 한다. 자동 계산은 선택된 규칙과 수치를 정확히 반영하고, 목표·약점·부위·서사 결과처럼 테이블이 판단할 부분은 선택 가능한 상태로 남겨야 한다.

JTBD의 기능적 일은 “불확실한 행동을 판정하고 결과를 정확히 다음 장면에 반영한다”다. 정서적 일은 규칙·자원 계산을 놓칠 부담을 줄이는 것이다. 사회적 일은 참가자의 대화와 공동 해석을 끊지 않고, 근거가 필요한 순간에 원문을 확인하는 것이다. 정서·사회적 효과는 향후 실제 플레이 관찰로 검증할 가설이다.

### How Might We Questions

1. 어떻게 하면 사용자가 먼저 행동을 이야기하고, 불확실할 때만 카드를 뽑게 할 수 있을까?
2. 어떻게 하면 실패의 결과를 본 자리에서 Push·결의·결과 수용을 판단할 수 있을까?
3. 어떻게 하면 사건과 징조를 지도 작성·주문 작성 화면을 찾지 않고 사용할 수 있을까?
4. 어떻게 하면 숨긴 선제권과 손패를 유지하면서 행동·대응·피해 적용을 연결할 수 있을까?
5. 어떻게 하면 목표·본능·관계를 생성 이후에도 자주 확인하는 살아 있는 정보로 만들 수 있을까?
6. 어떻게 하면 모바일에서 핵심 도구를 먼저 제공하면서, 데스크톱에서는 인물 정보를 함께 볼 수 있을까?
7. 어떻게 하면 빠른 규칙 요약을 즉시 열고, 필요한 경우에만 제공된 원문으로 확인할 수 있을까?
8. 어떻게 하면 오래된 저장 상태를 보존하면서 새 절차와 계산을 정확히 반영할 수 있을까?

### Key Insights

문제는 자료 부족보다 우선순위와 절차 연결의 실패였다. 앱에는 많은 표가 이미 있었지만, 실제 사용 빈도가 높은 사건·징조·결과 후 결의는 낮은 위치에 있거나 빠져 있었다. 생성·관리·참조의 경계를 사용자 과업에 맞게 다시 잡아야 했다.

입력 항목을 줄일 때는 무엇을 자동으로 알아도 되는지 구분한다. 기록된 능력치와 방금 판정한 대상·피해는 다시 묻지 않아도 된다. 반면 반응 판정 문양, 방어자가 고를 신체 부위, 사건·주문·괴수 재능의 구체적 의미는 룰북이 고정하지 않으므로 앱이 임의로 대신 정하지 않는다.

핵심 정보는 “현재의 값과 다음 선택”이며 전체 목록은 보조 참조다. 모든 재능·괴수·장비 목록을 항상 펼쳐 놓는 것보다, 현재 인물의 해금 재능·보유 장비와 장면에 맞는 도구를 먼저 보여주는 것이 적절하다.

## 💡 IDEATE: Generate Solutions

### Selected Methods

Brainstorming으로 해결안을 넓게 만든 뒤 SCAMPER Design의 Combine·Eliminate·Reverse 관점으로 기존 중복과 순서를 재검토했다. Analogous Inspiration에서는 작업대의 “행동 도구 옆에 필요한 상태를 둔다”는 원리와 체크리스트의 “한 번 처리한 항목을 다시 처리하지 않는다”는 원리를 검토했다. Affinity Clustering으로 접근, 절차, 인물, 세션, 관리 영역을 묶었다. 이 과정은 사용자 선호 투표가 아닌 근거 기반의 설계 작업이다.

### Generated Ideas

1. 기본 진입점을 인물 생성에서 실제 플레이 탁자로 옮긴다.

## 🛠️ PROTOTYPE: Make Ideas Tangible

### Prototype Approach

Storyboarding으로 일반 행동·탐사·전투·정산의 과업 연결을 정리하고, Role Playing에 해당하는 인물·심판 역할별 자동화 시나리오를 작성했다. 실제 참가자가 역할극에 참여한 것은 아니다. 정적 스케치에서 끝내지 않고 현재 React 앱의 작동 코드를 프로토타입으로 수정했다. 저장, 계산, 손패, 결과 갱신처럼 충실성 검증이 필요한 부분은 가짜 데이터 표시로 대신하지 않았다.

`App.tsx`는 상태·절차·작업 전환을, `PlayTable.tsx`는 라이브 플레이 도구와 현재 인물을, `QuickRules.tsx`는 검색 가능한 짧은 규칙을 담당한다. `rules.ts`의 순수 규칙 함수와 테스트는 계산을 담당하며 `index.css`는 공통 시각 체계를 제공한다. 로컬 한 인물 저장 구조와 기존 암호화된 원문 reader를 유지한다. 다중 인물 캠페인 서버, 참가자 간 실시간 동기화, 원격 비공개 손패는 구현 범위에 포함되지 않는다. 캐시된 production shell의 offline reload·기존 캠페인 보존·규칙 검색·6개 화면 내비게이션은 별도 6개 smoke 체크를 통과했다. 방문하지 않은 카드 이미지와 암호화 원문 해제까지 offline으로 검증한 것은 아니다. 근거: [오프라인 smoke 보고서](validation/offline-smoke-report.json).

### Prototype Description

기본 내비게이션은 플레이, 전투, 인물, 탐사, 비술, 휴식·정산으로 바뀌었다. 저장·원문·모험 기록·무결성·새 모험은 더보기에 모았다. 공통 상태 줄에서 현재 인물, 플레이어와 심판의 결의, 이동력·부상, 날짜·세션을 확인한다. 인물이 없으면 단계 안내와 인물 만들기 행동을 제공한다.

플레이 탁자에서는 문양과 실제 능력치를 고르고 바로 일반 판정을 뽑는다. 도움은 뽑기 전에 선언하고, 결과 옆에서 실패를 받아들이거나 한 번 Push하거나 결의를 쓴다. 전투 중에는 일반 뽑기를 차단하고 전투 손패 공간으로 연결한다. 사건·징조·환경·시간은 한곳에 있으며 최근 카드 이름과 표 결과를 함께 보인다. 데스크톱은 도구와 인물 요약을 나란히, 모바일은 기본 도구를 먼저 보여준다.

활성 목표의 완수·불가능, 본능의 문제·이야기 변화, 해금 재능, 지속 부상, 보유 무기·갑옷·흠집, 친구 도움을 탁자에서 처리한다. 전투는 목표·손패·숨긴 선제권·행동·대응·결과·피해 순서를 지원한다. 결과 이후 플레이어 결의 +1과 Nimble의 선제권 교체를 구현했다. Sally Forth는 라운드마다 한 번 사용을 추적하며 추가 행동 선언을 기록한다. 룰북이 추가 판정 카드의 획득 절차를 지정하지 않으므로 새 카드를 임의로 지급하는 자동 규칙은 만들지 않았다. 그 추가 행동의 내용과 필요한 판정은 심판과 확인한다.

원문은 기존 보호된 reader에서 제공하고, 빠른 요약은 별도 패널에서 바로 읽는다. 암호 없이 암호화 원문을 열었다는 뜻이 아니다. 규칙 검색, Escape 닫기, 포커스 순환·복귀, 본문 건너뛰기를 제공한다. 시각 체계는 밝은 종이색 표면, 짙은 숲색 masthead, 중립 경계선, 절제된 금색·녹색 강조, 한국어 본문과 제목의 분명한 위계다. 검증에서는 색·폰트·장식의 취향보다 읽기와 조작에 필요한 공간을 우선한다.

최종 규칙 재감사 이후 비전 주문·강력한 Undo Magick·봉인 주문의 전투 손패 경로, Disarming Presence의 실제 반응 +3, 괴수 갑옷의 부위별 흠집 key와 기존 저장 이행, 막간 목표 완수의 다음 세션 결의 지급, oracle 광대 이후 반복 숫자 상태 초기화를 추가했다. 최신 소스의 확장 검증은 128개 브라우저 체크를 통과했다. 주문·Undo·봉인 경로, Magick 없이 봉인 주문 사용, +3 실제 적용과 중복 비용 방지, 부위별 갑옷 독립, 막간 목표의 이월 지급은 실행으로 확인했다. 오래된 갑옷 key 이행·oracle 광대 반복 상태 초기화는 추가 소스 검토 항목이며, 해당 실행 결과를 별도 확인하지 않은 항목까지 128개 체크의 증거로 확대하지 않는다.

## ✅ TEST: Validate with Users

### Testing Plan

이 단계의 실행 대상은 자동화된 실제 앱이다. 사람 5–7명의 usability session을 진행했다고 주장하지 않는다. 동결 기준선과 수정 앱에서 지정된 시작 상태·과업·viewport를 사용하고, 컨트롤 수·탭 이동·요소 Y 좌표·overflow·오류·상태 갱신을 비교했다. 최신 소스와 실제 테스트 소스가 같은지 확인했고, 최종 브라우저 시나리오 128개 체크, 빌드·TypeScript·린트, 3개 파일의 규칙·인증 테스트 31개가 통과했다. 전체 신규 적 준비·공격 과업의 총 컨트롤 수는 기준선과 같은 방식으로 다시 계수하지 않았으므로, 해당 경로의 클릭 감소율은 주장하지 않는다.

### Key Learnings

현재까지 확인된 사실은 책의 목차와 표가 그대로 좋은 라이브 내비게이션이 되지는 않는다는 점, 가로 overflow가 없어도 매우 긴 세로 화면은 반복 작업을 어렵게 만든다는 점, 원문 보호와 읽기 쉬운 operational summary를 함께 제공할 수 있다는 점이다. 판정·사건·징조와 목표·결의는 책에서 다른 장에 있어도 실제 플레이에서는 연결된 작업이다.

수치 자동화의 정확성과 UX의 정확성은 함께 검증해야 한다. 덱·자원·부상 계산이 틀리면 빠른 버튼은 잘못된 결과를 더 빠르게 만든다. 반대로 정당한 계산이 있어도 결과와 다음 선택이 떨어져 있으면 사용자가 이를 활용하기 어렵다.

추론의 한계도 남는다. 한 인물의 로컬 도구를 그룹 전체의 실시간 판정 서버로 볼 수 없고, Sally Forth나 괴수 재능처럼 추가 절차가 명확히 수치화되지 않은 규칙을 편의를 위해 발명할 수 없다. 이러한 경계는 짧은 문맥 안내와 원문 접근으로 다룬다. 실사용자 테스트에 의한 설계 가설 검증은 후속 파일럿에서 가능하다.

### Refinements Needed

실행 중 발견한 모바일 화면 이동·포커스 문제는 손패→행동 및 결과→피해의 자동 scroll·focus 전달로 수정했고, 최종 시나리오에서 통과했다. 340px까지 가로 overflow와 긴 카드·문구 배치를 확인했다. 초기 기준선과 달리 판정 버튼이 모바일 첫 viewport 안에 들어오며 사건과 징조는 다음 구역에서 사용할 수 있다. 목표·본능은 모바일에서는 도구 뒤에 남아 있으므로 모든 정보가 첫 화면에 있다고 주장하지 않는다.

다음 실제 플레이 파일럿에서는 솔로·플레이어·심판의 역할을 구분해 관찰할 수 있다. “판정이 필요한가”, “실패 뒤 무엇을 고르는가”, “본능이 결의를 주는 시점은 언제인가”를 도움 없이 판단하는지 확인하고, 탐색 경로·대화 중단·잘못 누른 조작을 기록한다. 이 제안은 후속 승인이나 사용자 모집 계획을 뜻하지 않는다.
